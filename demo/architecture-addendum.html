Ehitame lepingu­platvormi.
Kinnisvara on esimene vertikaal.

ThinkOne pikem eesmärk ei ole kinnisvaratarkvara, vaid lepingute platvorm — haldus, dokumendid, hiljem RAG. Kinnisvara testime emaettevõtte peal. Järgmised vertikaalid (teenuslepingud, seadmed, parkimine) peavad tulema peale konfiguratsioonina, mitte uue arendusena.

Põhiidee: tuum ei tea, mis on „pind"

Kaks kihti. Tuum tunneb lepinguid. Vertikaal tunneb ruutmeetreid. Piir nende vahel ongi kogu platvorm.

·Üksusetüübid: hoone, üüripind (m², hind, korrus…)
·Lepingutüübid: hinnapakkumine, üürileping

⚖
Reegel koodis: domain/contracts/ ei tohi kunagi importida domain/realestate/. Vertikaal impordib tuuma. Üks rida kihistamisreeglisse — aga see rida ongi platvorm.
01

contract + tüüp, mitte ainult lease

Praegu on quote ja lease ainsad lepinguvormid ning põhitingimused arvutatakse koodis. Uues mudelis ütleb lepingu tüüp, mis parameetreid ta kannab.

Enne
lease
├─ space_id ← kinnisvara
├─ rent ← kinnisvara
├─ utility ← kinnisvara
└─ indexation
Pärast
contract
├─ contract_type · nt "yyrileping"
├─ status, parties, clauses…
└─ params (JSONB, valideeritud
tüübi skeemiga)
──────────────────────────
yyrileping skeem:
{ hind, tagatis_kuud,
indeks: {…}, hinnagraafik: […] }

V1-s on ainult üks tüüp — see on OK. Oluline on, et õmblus eksisteerib.

Tõestus prototüübist

Lame rent-veerg purunes juba demos. Vajasime astmelist üüri (1.–12. kuu 7,50 €/m², edasi 8,00), pakkumuse-põhist erihinda ja kontaktisiku ülekirjutust — kõik nõudsid struktuuri, mitte numbrit veerus. Parameetrid peavad olema skeemiga struktuur.

02

Hõive (claim), mitte space_id veerg

Leping ei viita esemele veeruga — leping hõivab eset. Hõivel on iseloom, periood ja kogus.

Enne
lease.space_id (täpselt 1)

seos = veerg tabelis;
eksklusiivsus kõvas koodis;
parkimine = parking_spots INT
Pärast
claim
├─ contract_id
├─ unit_id
├─ iseloom: exclusive | quota | shared
├─ periood: algus … lõpp
└─ kogus: (quota puhul)

Miks see loeb — sama primitiiv katab kõik tulevased juhud:

LepingEseHõive
ÜürilepingPind 4exclusive · 60 kuud
Parkimise annekstTsoon Aquota · 4 kohta
HoolduslepingHoone T6Bshared
TeenuslepingTeenus „IT-tugi"quota · 20 kasutajat

Reegel „üürileping = täpselt 1 eksklusiivne pind" jääb alles — aga vertikaali valideerimisreeglina, mitte tabeliskeemas. space.parking_spots INT kaotada: parkimine on tulevikus omaette üksusetüüp (tsoon) + quota-hõive.

03

Staatus on tuletis, mitte väli

Pinna olekut ei salvestata ega uuendata käsitsi — see arvutatakse aktiivsetest hõivetest. Siis ei saa ta kunagi valeks minna.

staatus(„Pind 4") = projektsioon aktiivsetest hõivetest ajas
ei ühtegi hõivet→Vaba
hõive pakkumusest→Pakkumusel
hõive lepingust (draft)→Lepingus
hõive lepingust (live)→Üüritud

Vajadusel cache kiiruse jaoks — aga tõde elab hõivetes. Konfliktikontroll (kaks eksklusiivset hõivet kattuvad; kvoodisumma > maht) tuleb tuumast tasuta, igale vertikaalile.

04

Mallid lepingutüübi külge

template.property_id → template.contract_type (+ konto). Mallid kuuluvad loogiliselt lepingutüübi ja ettevõtte alla; objektipõhine mall võib jääda valikulise ülekirjutusena, aga mitte ainsa kohana.

05

Klausli päritolu laiendatav

clause.source: template | negotiated | imported

imported on tulevase pärand-lepingute impordi ja kogu RAG-visiooni uks. Praegu maksab see ühe enum-väärtuse; hiljem avab terve tootesuuna — vanad PDF-lepingud loetakse samasse klauslimudelisse, mille peal kõik muu juba töötab.

∎

Piirid selgeks

Mida praegu MITTE ehitada

  • teist vertikaali (aga skeem peab teda kandma — ülaltoodu ongi selle test)
  • üldist registri-UI-d ega reeglimootorit
  • import-konveierit ja portfelli-RAG-i
  • parkimise geomeetriat ja jooniseid

Mis jääb architecture.md-st samaks

  • klauslipuu + tuletatud numbrid + id-viited
  • kolm renderdajat, üks nummerdusfunktsioon
  • olekumasinad ühe teega, Procrastinate-outbox
  • audit, allkirjastamine, agent, deploy

Kõik see on juba platvormi-kvaliteediga.
